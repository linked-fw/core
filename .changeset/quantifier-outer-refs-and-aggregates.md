A quantifier (`some`/`every`/`none`) whose callback reads the outer subject (`Person.select().where((p) => p.friends.some((f) => f.name.equals(p.name)))`) now compares with the outer subject; it used to compare the member with itself (a silent wrong answer), in a top-level where, a mutation's where and an ask. A quantifier on the outer subject's relation written inside another one (`p.friends.some((f) => p.bestFriend.friends.some((x) => x.equals(f)))`) starts at the subject; it started at the member. A nested quantifier may read the enclosing quantifier's member (`p.friends.some((f) => f.friends.some((g) => g.name.equals(f.name)))`), and a quantifier inside an inline filter may read the outer subject and the filter's member (it was refused). Inside a quantifier, comparing a member with the outer subject (`p.friends.some((f) => f.bestFriend.equals(p))`) compares with the subject, not the member. Such a query has no DSL-JSON form yet: `toJSON()` refuses it (a top-level one used to serialize the self-comparison). An aggregate inside a quantifier (`p.friends.some((f) => f.friends.size().equals(1))`), an inline filter or a `minus()` is refused at lowering with an error naming the construct and pointing at a top-level `.where((p) => p.friends.size().equals(1))`; it used to emit `FILTER(COUNT(…))`, which is not valid SPARQL.
